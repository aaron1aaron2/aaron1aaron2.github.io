# 新增專案

1. 先在非公開經歷正本核對問題、本人責任、團隊／第三方歸屬、產物、日期與驗證狀態。素材不足時保持未知，不由一張圖推定本人主導或已部署。
2. 複製[專案模板](templates/project.md)，先完成內容，再決定是否適合首頁代表案例；完整列表與案例內頁必須連得起來。
3. 為本案整理架構說明與專屬流程圖。有UI／UX時找原始截圖，依[圖片規則](MEDIA_POLICY.md)決定原圖、去識別原圖或明示的示意圖。
4. 列表選1–3張，順序為現場照片、實際畫面、架構／流程。寫出每張的用途、替代文字、出處及必要限制，不用重複圖片湊滿。
5. 同時建立中文與英文頁；原始圖保留原語言，標題、圖說與操作文字需有對應英文。導覽與相關案例保持目前語言。
6. 更新列表條目、必要的首頁摘要及相關案例。固定三層格式見[閱讀規則](PROJECT_STRUCTURE.md)。不變更其他作品的責任或日期。
7. 檢查桌面／手機、圖片上一張／下一張、單張控制隱藏、方向鍵、點圖浮層、關閉還原、類型／時間檢視與語言切換。另檢查列印與無JavaScript閱讀；未驗證的項目明示。
8. 提交前檢查diff、圖片大小、敏感內容與repo檔案清單。公開repo只收可公開的網站衍生檔及維護文件；原始內部素材、來源manifest與私人資料不隨發布上傳。
9. 發布後核對Pages結果、實際頁面與提交檔案。不要把本機已更新等同網站已更新。

## 本repo的形式

`public/` 是可直接部署的靜態輸出，Pages workflow不部署 `docs/`。內部建置／來源核驗在非公開工作區完成；若手動修改此repo輸出，也須同步內容正本並遵守相同規則，避免下次重建覆蓋。

新增檔案沿用 `project-<id>.html` / `project-<id>-en.html` 與 `assets/projects/`，不要把私人路徑、原始手冊或來源清冊寫到HTML。沿用 `styles.css`、`project-gallery.css/js` 與 `image-viewer.css/js`，不為單一案例建立另一套輪播或彈窗。

## 新案補充檢查

- 在填寫基本資料時列出有證據的技術／方法tag，三層讀者入口共用同一組；提案不填未實作框架。
- 先判定案例重點。技術導向使用架構與流程主圖；UI／UX案例找能完整解釋功能的實際畫面，基本資訊及主要分析圖表不可因裁切而遺失。
- 新研究發表建立獨立案例，從首頁研究區與列表連入，維護發表資訊及本人／團隊分工。常用技術分組的相關連結也同步檢查。

## 敘事收斂

先用一句話說明本案的主要問題，再沿情境、系統／介面、設計取捨、成果往下閱讀。正文與導覽順序相同。相關案例放最後，補充機制可展開；不要把產品總覽寫成所有子案的彙編。提交前檢查重複圖、重複責任／成果段及段落缺少標題的情況。


## 2026-11-19 旗艦平台的系統與功能深度

旗艦平台先說清楚產品目標與本人責任，再以模組表呈現系統／功能全貌；主架構、事件流程及具代表性的真實介面各回答不同問題。不得為精簡而把完整產品縮成單一UI功能。監控需區分資料通道、非同步工作佇列、特徵／WAV／FFT保存、事件執行狀態與資料完整度；RabbitMQ設計參與不推定所有部署均使用同一broker。出廠檢測需交代計畫→工單→待測物、執行紀錄、階段／測點、基準錄製／確認／版本、門檻與判定、偏離定位及教學。三層主要UI不等於工單三分頁或三層判讀。文件中的能力、現場已驗證能力與正式驗收必須分開。
