# 專案閱讀結構與固定格式

## 首頁：快速認識

先交代定位、正式職稱、代表工作與經歷，再用六個代表案例說明能力。每案順序固定：**專案情境 → 核心問題 → 遇到困難 → 我的工作 → 成果**。研究與競賽沿用相同欄位；團隊獎項不改成個人獎項。

首頁保留代表性，完整廣度放列表，技術細節放內頁。不要在三層複製整段相同敘述。

## 專案列表：橫向比較

每案固定名稱、類型、紀錄時間、產品關係、圖片及三欄：**核心問題 → 我的工作 → 成果**。保留類型／時間檢視與分類／年份跳轉。同一個專案只有一份條目，切換檢視時移動原條目，圖片狀態也應保留。

圖片1–3張，選擇與順序依[圖片規則](MEDIA_POLICY.md)。圖片與文字形成一個條目，不額外建立重複的近期作品或代表作品列表。

## 案例內頁：逐步深入

首屏固定：類型、專案名稱、概要、我的工作、成果與狀態、紀錄時間。紀錄年不冒充專案起訖。

正文與導覽採同一閱讀順序：

1. **情境與目標**：一個主要問題，以及本案要讓誰完成什麼。深度案例可用2–4點說明主線。
2. **系統與流程**：先解釋輸入、處理及產出，再放專屬流程圖。研究原圖或實際成果圖各有用途，不重複。
3. **介面與互動**（適用時）：完整功能畫面如何支援操作、判斷及防錯。
4. **關鍵設計取捨**：2–3個有據故事，各說明挑戰、方法與取捨、結果。團隊方法不自動變成個人發明。
5. **成果與驗證**：交付及實際驗證、資料與適用範圍。原型、整合、現場示範、正式部署與驗收分開。

相關案例放成果後；先完成本案，再邀請讀者深入其他題目。補充機制放可展開的技術細節，不另堆一組相同層級的主章節。平台頁說明產品與整合責任，RUL、報告及AI治理等子案用摘要與連結承接，不複製子案全文。

原始架構圖、模型圖、現場照片及領域深入章節按用途保留，不重複放同一張流程圖。第三方模型、共同作者、工程夥伴及AI協作保留必要歸屬。

## 共通規則

- 中英頁成對，頁首、相關案例、圖說、按鈕與替代文字齊全；切換保留所在案例及可用片段。
- 同層字級、欄位、留白與麵包屑對齊使用共用樣式。
- 不編造準確率、效益、錄取率、ATS通過或驗收狀態。
- 圖片點開仍留在原頁。圖片不得靠裝飾取代系統說明。

## 技術標籤與研究索引

每案維護一組有來源的技術／方法關鍵字，在首頁代表案例、列表及內頁首屏一致呈現。使用可換行的靜態標籤，不偽裝成可點擊的分類或能力評分。提案可用規格、流程、權限方法，不虛構未實作的程式框架。

首頁研究與發表逐篇保留年份、發表場所、研究問題、本人工作及獨立案例入口；論文方法屬團隊時須明示。碩士論文另作研究案例，不假稱期刊發表。常用技術依應用分組、連到相關作品，不將過往使用一律寫成目前精通。

技術導向案例可不設操作介面章節，列表直接以架構／流程圖為主。產品操作案例的截圖則保留完整功能脈絡，避免只剩按鈕或空圖。
