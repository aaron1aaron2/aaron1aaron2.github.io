情境與目標

設備維護需要先掌握狀態、追查異常，再取得分析與報告；這些步驟必須連成可持續運作的產品流程。

  • 看見設備狀態：從總覽辨識需要處理的設備，再深入趨勢與資料。
  • 接續分析與報告：耗時工作另外派工，保留進度、結果與歷史。
  • 維持產品演進：處理資料同步與控制權，逐步解除 1.0 依賴。

把排程時間與任務狀態分開

挑戰多感測器報告與壽命分析需要排程、手動執行、批次及歷史紀錄；觸發器本身不足以代表任務進度。

方法與取捨以資料庫保存排程狀態，將觸發器與任務生命週期分工。我建立有狀態排程，參與派工、回呼及產物串接；讓排程器負責觸發，資料庫保存可查詢狀態。

結果形成支援感測器排程、手動觸發與歷史的工作流；排程執行與分析服務責任可以分別追查。

大檔分析不再綁住上傳請求

挑戰大型原始波形上傳同時負擔雜湊、儲存與處理，容易讓請求等待和後續工作耦合。

方法與取捨參與將大型資料改為非同步接收，並用任務身分與進度回報承接後續處理。我負責資料接收契約、容量、安全與狀態機的跨團隊決策；後續 server 實作交由工程夥伴。

結果完成非同步接收的狀態、去重與進度對帳契約，並以壓測支持設計方向；後續服務實作由工程夥伴承接。

即時概況與長時間分析分開

概況回答現在需要處理什麼；長時間分析回答狀態如何變化。查詢先呈現摘要，耗時分析另建任務，保存結果、進度與缺資料狀態。

平台狀態是指令依據

指令與確認以平台持久狀態及 HTTP 路徑為準，MQTT 作喚醒通知，定期 heartbeat 補足通知失落。完整狀態更新與獨立波形請求採不同覆蓋規則；完整運行範圍依版本另驗。

共同建構與交付的分工

我主導產品與領域設計，負責排程、跨服務工作流、資料同步及整合驗證。主管提供初始方向，設計師參與主儀表板；工程夥伴負責各自服務與基礎設施，AI agents 參與實作及測試，變更由人工審查後決定發布。

新舊系統如何銜接

2.0 的新功能建構，與舊系統的相容、遷移及替換同時推進。

  1. 01

    新舊共存

    同步設備與資料，先保護 2.0 新增的設定及功能。

  2. 02

    逐步替換

    轉移設備控制權，建立遷移稽查，將功能改接 2.0 原生流程。

  3. 03

    獨立運作

    目前 2.0 已可不依賴 1.0，持續新增功能及版本交付。

先界定資料由誰更新

我建立資料同步與欄位保護，明確區分舊系統可更新的內容與 2.0 自己管理的設定，讓共存期間的新功能與使用者設定能被保留。

把設備控制權移到 2.0

我參與重整設備管理與控制權責，將狀態轉移規則收斂到 2.0，逐步縮小舊系統的責任；與工程夥伴依各自分工完成整合及驗證。

讓舊資料遷移能被查核

整合遷移清單與檢查工具，要求感測器有明確對應；缺號或對應不明時中止並回報，補正清單後重新驗證，降低設備資料錯置風險。

    將設備告警接成可追溯的局部放電分析任務，讓使用者同時知道分析結果與資料是否完整。

    聊天室需呈現等待及工具回饋，避免把內部文件與引用標記當成使用者答案。

    建立專案與 issue 紀錄架構，連結每日所有功能回歸、並行修復與驗證，以及人工審查與發布決策。

    面向設備出貨前的逐件檢測，整合受測件、量測批次、基準比對、判定與報告；本人主導需求到現場交付。
